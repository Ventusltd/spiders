## What this estate is

Eight active git repos, one federation. `globalgrid2050` (4,524 commits since 2026-03-12) is the historical core and public homepage/catalogue. `gridatlas` ships the spatial/electrical map product via an immutable-shell, hashed-cartridge release system (a `v9.NNN` version plus a 12-digit `YYYYMMDDHHMM` "generation" id). `pipelinenews` owns governed project/news evidence. `spiders` scrapes. `data-grid-gb` and `grid-distance-maths` own authoritative network data and geodesy respectively. `cvaa` is the estate's own immune system — a registry of "vaccines," each a named failure mode plus an executable check, that consumer repos run against themselves. `ventus-grid-engine`, created today, is the newest organ: extracted pure grid-engine maths and the Pipeline↔GridAtlas deep-link contract, pulled out of two apps that had each silently grown their own copies of both.

Five more directories at the GitHub root (`gridatlas-codex-202609020010-r2`, `gridatlas-v9104-fullscreen`, `pipelinenews-codex-202609020010-r2`, `pipelinenews-codex-202609020100-r3`, `pipelinenews-worktrees`) are full application copies with no `.git` of their own — sibling snapshots, not repos.

## How it got here (six-month-mutations.md)

globalgrid2050's history reads as a sequence of eras, each nameable from its own commits: a bootstrap content era (from 2026-03-12); a sandbox-clone era from 04-24 where every experiment became a full `vN` directory clone ("full clone of stable V6"); an automated-gridbot era (May–June, the highest-volume period — 1,443 and 1,560 commits respectively) driven by scheduled data-feed bots; a quiet manual-content July (46 commits, a ~30x collapse); a short, dense "V11 validation authority" burst in early August; a 110-commit-in-one-day V5→V9 UI-parity reconciliation burst on 08-22, forced by prior forking finally needing to be reconciled; and, from 08-24, a multi-repo split era where globalgrid2050 stops carrying the app itself and starts hosting sync/catalogue workflows pointing at newly-born standalone repos (pipelinenews, gridatlas, cvaa, grid-distance-maths, data-grid-gb, ventus-grid-engine — one new repo roughly every day or two).

The dominant genome marker is **redo-by-clone, not edit-in-place**. `repd_grid_atlasv6/v7/v8/v9` were each created as a "full clone of stable" predecessor. `uk_energy_tracking` was forked six times (`_v2` through `_v6_2`). `repd_grid_atlasv9` was deleted from globalgrid2050 on 2026-05-09 and reappeared, four months later, as the standalone `gridatlas` repo. The estate's stress-point files match this pattern exactly: `REPO_STRUCTURE.txt` (550 revisions) and `index.html` (227) churn on every reorganisation; the rest of the top 20 is the `uk_energy_tracking_vN` bot-feed family, each generation independently racking up 138–186 revisions rather than one file being updated in place.

## Where this estate is fragile

**The single most fragile thing is the estate's shared ordering mechanism.** `monotonic-utc-generations` fails on all 8 repos tested with zero exceptions — including a repo created *today* — with generation timestamps running up to ~40 hours off actual commit time and sometimes backwards. Every cross-repo mechanism in this estate (release names, scope-of-works filenames, workflow filenames, the `v9.NNN`/generation pointer gridatlas ships by) depends on these 12-digit ids as the *only* ordering and identity signal there is, and it is measurably wrong everywhere.

Close behind: `gridatlas`'s live release pointer names a checksummed release directory whose checksums do not currently verify (`pointer-verifies` FAIL); a real navigation-emptying outage has already happened once from an inline-JS-data-block edit and the pattern that caused it (string-surgery on structured data) is still how these repos publish; and CVAA's own registry has one vaccine — `disk-is-not-what-ships`, fittingly about the gap between what's on disk and what ships — that exists only as an uncommitted file in one local checkout, invisible to `origin/main` and to any other clone. And `no-app-copies`, the vaccine written specifically against copy-instead-of-extend, has a confirmed blind spot: it only looks inside one repo, so it reports "immune" against five full sibling-repo application copies sitting at the GitHub root doing exactly what it exists to catch.
